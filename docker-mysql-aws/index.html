Nginx, MySQL, phpMyAdmin y Flask con Docker, en AWS

Autor: Pablo Pedernera · Nivel: intermedio · Tiempo estimado: dos partes de unos 60 minutos cada una

Esta práctica es la versión AWS de "Nginx, MySQL, PhpMyAdmin y Flask con Docker" de Killercoda. Los servicios son los mismos; lo nuevo es que la máquina la creás vos, en la nube de Amazon Web Services, y la vas a ver desde tu PC como cualquier servidor de Internet.

Antes de empezar

  • Hacela desde tu PC (Windows, Linux o Mac), con un navegador actualizado (Chrome, Firefox o Edge). No se puede hacer desde el celular.
  • Necesitás estar inscripto en la clase de AWS Academy Learner Lab de tu materia. Si no te llegó la invitación de notifications@instructure.com, revisá spam y avisale al docente.
  • Cada paso termina con un ✔ Verificación. No sigas al paso siguiente si la verificación no te da lo esperado: andá a Problemas comunes.
  • Tenés crédito limitado. Al terminar, hacé el Paso 11 (apagar todo), aunque vayas a seguir otro día.

De Floci a AWS real

En AWS y Cloud Computing — Introducción y en S3 + IAM en profundidad trabajamos con Floci, un emulador de AWS que corre en Docker dentro de Killercoda: imita la API de S3 e IAM, pero no hay servidores, redes ni IPs de Amazon detrás.

Esta práctica es en AWS de verdad, a través del AWS Academy Learner Lab: la misma consola que usan las empresas, en los centros de datos de Amazon, con un crédito que da el Terciario y sin tarjeta de crédito.

En esta práctica no usamos AWS CLI. Todo lo de AWS (la VPC, el security group, la instancia, apagarla) se hace con clics en la consola web, para que veas cada pieza en pantalla. Los comandos que vas a escribir en la terminal (Pasos 6 a 10) no son de AWS: son de Linux y Docker, dentro de tu servidor, como en Killercoda.

Qué vamos a tener al final

Una máquina Ubuntu en AWS con cuatro servicios en Docker, accesibles desde tu navegador:

  • Nginx sirviendo una página web en el puerto 80
  • MySQL como motor de base de datos (sin puerto expuesto a Internet)
  • phpMyAdmin para administrar MySQL en el puerto 8080
  • Una aplicación Flask con un CRUD conectado a MySQL en el puerto 8888

La práctica tiene dos partes, que podés hacer en días distintos:

  • Parte 1 (Pasos 1 a 5): la red, el firewall y el servidor. Es lo propio de AWS.
  • Parte 2 (Pasos 6 a 11): Docker y los servicios, más un desafío final.

Los nombres de la consola. La consola de AWS aparece en el idioma de tu navegador. En la guía va el nombre en español y, entre paréntesis, en inglés: por ejemplo Reglas de entrada (Inbound rules). Si alguna palabra no coincide exacto, guiate por la otra versión o por la ubicación en la pantalla.

Paso 1 — Entrar al Learner Lab

  1. Entrá al link del mail de invitación (o a https://www.awsacademy.com/, Iniciar sesión → Student Login) con la cuenta que creaste al aceptarla.
  2. Abrí el curso AWS Academy Learner Lab → Módulos (Modules) → Iniciar el Laboratorio de aprendizaje de AWS Academy (Launch AWS Academy Learner Lab). Aceptá los términos si te los pide.
  3. Arriba, hacé clic en Start Lab. El círculo al lado de AWS pasa de rojo a amarillo y después a verde (tarda unos minutos la primera vez).
  4. Con el círculo en verde, hacé clic en AWS: se abre la consola de AWS en otra pestaña. Si el navegador bloquea la ventana emergente, permitila.
  5. Arriba a la derecha de la consola, verificá que la región sea EE. UU. Este (Norte de Virginia) / N. Virginia (us-east-1). El Learner Lab solo permite EC2 en us-east-1 y us-west-2.

En el panel del lab también ves el crédito usado (Used $0 of $50) y el tiempo restante de la sesión (4 horas). Si se termina, volvé a hacer clic en Start Lab. Las horas que muestra AWS Details están en hora del Pacífico, no de Argentina: guiate por el tiempo restante.

La terminal que aparece a la izquierda del panel del lab no es tu PC ni tu servidor: es una máquina del Learner Lab. En esta práctica no la usamos.

✔ Verificación: estás en la consola de AWS, región us-east-1.

Paso 2 — Conocer la red: la VPC por defecto

Toda instancia EC2 vive dentro de una VPC (Virtual Private Cloud): una red privada tuya dentro de AWS. No hace falta crear una: cada cuenta trae una VPC por defecto, ya preparada para tener máquinas con salida a Internet. La vamos a usar tal cual, pero veamos qué tiene.

  1. En el buscador de la consola escribí VPC y entrá.
  2. Abrí Sus VPC (Your VPCs): vas a ver una con VPC predeterminada (Default VPC) = Sí (Yes) y un bloque de direcciones como 172.31.0.0/16.
  3. Abrí Subredes (Subnets): hay una subred por cada zona de disponibilidad (us-east-1a, us-east-1b, …), cada una un pedazo del /16 (por ejemplo 172.31.0.0/20).
  4. Abrí Puertas de enlace de Internet (Internet gateways): hay una conectada (Attached) a la VPC por defecto. Es la "puerta" de la VPC hacia Internet.
  5. Abrí Tablas de enrutamiento (Route tables), elegí la de la VPC por defecto y mirá la pestaña Rutas (Routes):
    • 172.31.0.0/16 → local: el tráfico dentro de la VPC se queda adentro.
    • 0.0.0.0/0 → igw-…: todo lo demás sale por la puerta de enlace de Internet.

Es lo mismo que en una red de casa: una red privada, un router con una ruta por defecto hacia Internet. Acá cada pieza tiene nombre propio.

✔ Verificación: anotá el bloque de la VPC por defecto y el ID de la puerta de enlace de Internet (igw-…).

Paso 3 — Crear el security group (el firewall)

Un security group (en la consola en español, grupo de seguridad) es un firewall que se aplica a la instancia: por defecto bloquea todo lo que entra y solo deja pasar lo que vos autorices.

  1. En la consola, buscá EC2 → menú izquierdo Grupos de seguridad (Security Groups) → Crear grupo de seguridad (Create security group).

  2. Nombre del grupo de seguridad (Security group name): sg-docker-mysql. Descripción (Description): Practica docker-mysql. VPC: la VPC por defecto.

  3. En Reglas de entrada (Inbound rules), agregá estas cinco reglas. Mi IP (My IP) hace que AWS complete sola la IP pública de tu conexión.

    Tipo (Type) Puerto Origen (Source) Para qué
    SSH 22 Mi IP (My IP) SSH desde tu PC (Paso 5, opción B)
    SSH 22 Personalizada (Custom) → com.amazonaws.us-east-1.ec2-instance-connect Terminal en el navegador (Paso 5, opción A)
    HTTP 80 Mi IP (My IP) Nginx
    TCP personalizado (Custom TCP) 8080 Mi IP (My IP) phpMyAdmin
    TCP personalizado (Custom TCP) 8888 Mi IP (My IP) CRUD Flask

    La segunda regla usa una prefix list (lista de prefijos): en Origen elegí Personalizada y empezá a escribir ec2-instance-connect hasta que aparezca. Es la lista de IPs de los servidores de AWS desde los que se conecta la terminal del navegador; no es tu IP.

  4. Reglas de salida (Outbound rules): dejá la que viene (todo permitido hacia afuera; la instancia necesita descargar paquetes e imágenes).

  5. Crear grupo de seguridad (Create security group).

¿Por qué Mi IP y no 0.0.0.0/0 (cualquiera)? Porque phpMyAdmin entra a MySQL como root sin pedir contraseña. Abierto a todo Internet, cualquiera podría borrar tu base en minutos: hay robots escaneando IPs de AWS todo el tiempo. Si mañana te conectás desde otra red, vas a tener que actualizar estas reglas (ver Problemas comunes).

Por eso mismo, desde el celular u otra red no vas a poder entrar a tus servicios: el firewall solo deja pasar tu IP.

✔ Verificación: sg-docker-mysql aparece en la lista con 5 reglas de entrada. Si le pusiste otro nombre, no pasa nada: acordate cuál es, porque más adelante lo vas a buscar.

Paso 4 — Crear la instancia EC2 y "su sistema operativo"

En la nube no se instala el sistema operativo desde un pendrive: se elige una AMI (Amazon Machine Image), una imagen de disco con el sistema ya instalado, y AWS crea la máquina a partir de ella.

  1. En EC2 → Instancias (Instances) → Lanzar instancias (Launch instances).
  2. Nombre (Name): docker-mysql-<tu-apellido>.
  3. Imágenes de aplicaciones y sistemas operativos (Application and OS Images): elegí Ubuntu, y en la lista de abajo Ubuntu Server 24.04 LTS (HVM), SSD Volume Type, la que dice Apto para la capa gratuita (Free tier eligible), arquitectura 64 bits (x86). "SSD Volume Type" es parte del nombre: es la correcta. No elijas las variantes que dicen "SQL Server": no andan con una instancia chica.
  4. Tipo de instancia (Instance type): t3.micro (2 vCPU, 1 GB de RAM). Alcanza para esta práctica, con el ajuste de memoria del Paso 6.
  5. Par de claves (inicio de sesión) (Key pair (login)): elegí vockey. Es el par de claves que el Learner Lab ya creó para vos (no crees uno nuevo).
  6. Configuración de red (Network settings) → Editar (Edit):
    • VPC: la VPC por defecto.
    • Subred (Subnet): Sin preferencia (No preference) (o cualquiera de las subredes del Paso 2).
    • Asignar automáticamente la IP pública (Auto-assign public IP): Habilitar (Enable). Sin IP pública no podrías verla desde tu PC.
    • Firewall (grupos de seguridad): Seleccionar un grupo de seguridad existente (Select existing security group) → sg-docker-mysql.
  7. Configurar almacenamiento (Configure storage): cambiá a 16 GiB, tipo gp3 (las imágenes de Docker ocupan lugar; 8 GiB queda justo). En Sistemas de archivos (File systems) dejá Ninguno (None): S3, EFS y FSx son discos compartidos en red que esta práctica no usa y gastan crédito aparte.
  8. Revisá el resumen de la derecha (imagen Ubuntu sin SQL Server, t3.micro, vockey, tu security group, 16 GiB) y hacé clic en Lanzar instancia (Launch instance). Si cambiaste la imagen después de completar lo demás, revisá que no se hayan reiniciado el par de claves o el security group.
  9. Volvé a Instancias y esperá a que la instancia esté En ejecución (Running) y que Comprobación de estado (Status check) diga que pasaron las comprobaciones (checks passed) (un par de minutos).
  10. Seleccioná la instancia y anotá su Dirección IPv4 pública (Public IPv4 address) y su Dirección IPv4 privada (Private IPv4 address).

✔ Verificación: la instancia está En ejecución, con las comprobaciones pasadas, y tenés anotadas las dos IPs. La privada está dentro del bloque de la VPC del Paso 2 (172.31.x.x); la pública no. ¿Por qué tiene dos?

Paso 5 — Conectarte a la instancia

Opción A, recomendada: terminal en el navegador (EC2 Instance Connect).

  1. Seleccioná la instancia → Conectar (Connect) → pestaña EC2 Instance Connect.
  2. Nombre de usuario (Username): ubuntu → Conectar (Connect). Se abre una terminal en una pestaña nueva. Al pie de esa ventana figuran el ID de la instancia y sus IPs pública y privada.

Opción B: SSH desde tu PC. Es como se trabaja en la realidad. Puede no andar desde redes con proxy (como algunas redes de trabajo); en ese caso usá la opción A.

  1. En el panel del Learner Lab: AWS Details → Download PEM (baja labsuser.pem; el PPK es la misma clave para PuTTY, no lo necesitás).
  2. Desde una terminal en la carpeta donde quedó el archivo:
    • Linux / Mac:
      chmod 400 labsuser.pem
ssh -i labsuser.pem ubuntu@<IP-PUBLICA>
    • Windows (PowerShell):
      icacls labsuser.pem /inheritance:r /grant:r "$($env:USERNAME):R"
ssh -i labsuser.pem ubuntu@<IP-PUBLICA>
  3. La primera vez pregunta si confiás en el equipo: escribí yes.

✔ Verificación: en la terminal ves algo como ubuntu@ip-172-31-x-x:~$. Ejecutá hostname -I y comparalo con la IP privada del Paso 4.

Pensá lo que acabás de hacer: en unos minutos, y sin tocar un solo cable, tenés una computadora virtualizada completa, con un sistema operativo totalmente funcional, corriendo en un centro de datos de Amazon y con una IP pública en Internet. Eso es la infraestructura como servicio (IaaS): alquilar la máquina, no comprarla. En la Parte 2 le instalamos Docker y los servicios, igual que harías con un servidor propio.

Fin de la Parte 1. Si seguís otro día, apagá la instancia (Paso 11) y al volver leé "Si la volvés a prender otro día": la IP pública va a ser otra.

Paso 6 — Instalar Docker

La AMI trae Ubuntu limpio: Docker lo instalamos nosotros.

sudo apt update
sudo apt install -y docker.io docker-compose-v2 git python3-pip
sudo usermod -aG docker ubuntu
newgrp docker

El usermod agrega tu usuario al grupo docker, para no tener que poner sudo delante de cada comando de Docker. El newgrp docker hace que tome efecto en esta terminal sin tener que desconectarte; las próximas veces que te conectes ya lo toma solo.

Memoria de reserva (swap). La t3.micro tiene 1 GB de RAM y MySQL usa buena parte: sin más margen, phpMyAdmin se queda colgado. Creá un archivo de swap de 1 GB en el disco, que funciona como memoria de reserva (más lenta, pero evita que se cuelgue):

sudo fallocate -l 1G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

La última línea hace que el swap siga activo cuando apagues y vuelvas a prender la instancia.

✔ Verificación:

docker run --rm hello-world
docker compose version
free -m

El primero muestra Hello from Docker!; el segundo, la versión de Docker Compose; en el tercero, la fila Swap dice unos 1023 de total.

Paso 7 — Levantar MySQL, phpMyAdmin y Nginx con Docker Compose

mkdir -p ~/practica/web
cd ~/practica
nano docker-compose.yml

Pegá este contenido, guardá con Ctrl+O, Enter, y salí con Ctrl+X:

services:
  mysql:
    image: mysql:8.4
    restart: always
    environment:
      MYSQL_ROOT_PASSWORD: mysecretpassword
    networks:
      - mynetwork

  phpmyadmin:
    image: phpmyadmin/phpmyadmin:5.2
    restart: always
    ports:
      - 8080:80
    environment:
      PMA_HOST: mysql
      PMA_USER: root
      PMA_PASSWORD: mysecretpassword
    depends_on:
      - mysql
    networks:
      - mynetwork

  web:
    image: nginx:1.28
    restart: always
    volumes:
      - ./web:/usr/share/nginx/html
    ports:
      - "80:80"
    networks:
      - mynetwork

networks:
  mynetwork:

En Killercoda el archivo empezaba con version: '3'. Las versiones nuevas de Docker Compose ya no lo usan (si lo ponés, avisa que es obsoleto y lo ignora).

Las imágenes tienen versión fija (mysql:8.4, no mysql:latest). Con latest, si sale una versión nueva que cambia algo, la práctica deja de andar de un día para el otro sin que hayas tocado nada.

docker compose up -d

✔ Verificación: docker ps muestra tres contenedores (mysql, phpmyadmin, web) en estado Up.

Si ahora abrís http://<IP-PUBLICA> y ves 403 Forbidden, es lo esperado: Nginx ya anda, pero la carpeta web/ está vacía y no tiene nada para mostrar. La página la creás en el Paso 9.

Paso 8 — Ejecutar SQL desde phpMyAdmin

¿Cuál es la <IP-PUBLICA>? La de tu instancia, que anotaste en el Paso 4. Si no la tenés a mano: está al pie de la ventana de EC2 Instance Connect; o en EC2 → Instancias → seleccioná la instancia → Dirección IPv4 pública (Public IPv4 address); o desde la terminal de la instancia:

curl -s https://checkip.amazonaws.com

Ojo: cambia cada vez que la instancia se detiene y vuelve a arrancar.

  1. En el navegador de tu PC, abrí http://<IP-PUBLICA>:8080 (con http, no https).
  2. Vas a ver la pantalla principal de phpMyAdmin.
  3. Andá a la pestaña SQL, pegá estas sentencias y hacé clic en Continuar:
CREATE DATABASE alumnos;
USE alumnos;

CREATE TABLE alumnos (
  id INT PRIMARY KEY AUTO_INCREMENT,
  nombre VARCHAR(50) NOT NULL,
  apellido VARCHAR(50) NOT NULL,

CREATE TABLE materias (
  id INT PRIMARY KEY AUTO_INCREMENT,
  nombre VARCHAR(50) NOT NULL,
  calificacion FLOAT NOT NULL,
  alumno_id INT,
  FOREIGN KEY (alumno_id) REFERENCES alumnos(id)
);

INSERT INTO alumnos (nombre, apellido, fecha_nacimiento) VALUES

Paso 9 — Publicar una página con Nginx

nano ~/practica/web/index.html

Pegá este contenido:

<!DOCTYPE html>
<html lang="es">
<head>
  <meta charset="UTF-8">
  <title>Mi servidor en AWS</title>
  <script>
    window.onload = async function () {
      // La IP del servidor es la que escribiste en la barra de direcciones
      document.getElementById('servidor').textContent = window.location.hostname;
      try {
        // ipify devuelve la IP pública de quien hace la consulta: tu navegador
        const r = await fetch('https://api.ipify.org?format=json');
        document.getElementById('visitante').textContent = (await r.json()).ip;
      } catch (e) {
        document.getElementById('visitante').textContent = 'No se pudo obtener';
      }
    };
  </script>
</head>
<body>
  <h1>Hola desde EC2</h1>
  <p>IP pública del servidor: <strong id="servidor">...</strong></p>
  <p>Tu IP pública (visitante): <strong id="visitante">...</strong></p>
</body>
</html>

Abrí http://<IP-PUBLICA> en el navegador de tu PC.

✔ Verificación: la página muestra dos IPs distintas. Comparalas con lo que viste antes:

  • La del servidor, ¿es la Public IPv4 del Paso 4?
  • La del visitante, ¿es la que AWS puso como Mi IP en el security group (Paso 3)? (En redes con más de una IP de salida, como algunas redes de trabajo, puede cambiar al recargar: ver Problemas comunes.)

Paso 10 — Desplegar el CRUD con Python y Flask

cd ~
git clone https://github.com/pablopedernera0/crud-python.git
cd crud-python
pip install flask mysql-connector-python --break-system-packages

La aplicación tiene que conectarse a MySQL, que no expone su puerto: solo es accesible por su IP dentro de la red de Docker.

cd ~/practica
MYSQL_IP=$(docker inspect $(docker compose ps -q mysql) \
  --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
echo "IP del servidor MySQL: $MYSQL_IP"
cd ~/crud-python
sed -i -E "s/172\.18\.[0-9]+\.[0-9]+/$MYSQL_IP/" app.py
grep -n "172.18" app.py

El sed reemplaza en app.py cualquier IP 172.18.x.x por la IP actual de MySQL, así que lo podés repetir las veces que haga falta. El grep te muestra la línea que quedó: tiene que tener la misma IP que imprimió el echo.

Iniciá la aplicación con nohup, para que siga corriendo aunque cierres la terminal:

nohup python3 app.py > app.log 2>&1 &
sleep 3 && curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8888/

✔ Verificación: el curl devuelve 200. Abrí http://<IP-PUBLICA>:8888 en tu navegador: aparece el listado de alumnos que cargaste en el Paso 8. Probá crear, editar y borrar un registro, y fijate en phpMyAdmin que los cambios se ven también ahí.

Ya tenés tres IPs distintas en juego: la pública de la instancia (la que usás desde tu PC), la privada en la VPC (172.31.x.x) y la del contenedor de MySQL en la red de Docker (172.18.x.x). Las tres son de la misma máquina, vistas desde lugares distintos.

Desafío final

Esta parte no está resuelta en la guía: la tenés que pensar vos. Va en la entrega. Hacelo antes de apagar la instancia.

  1. Explicá por escrito por qué MySQL no necesita una regla de entrada en el security group ni una línea ports: en docker-compose.yml, y aun así phpMyAdmin y el CRUD llegan a él. ¿Por qué camino entra cada uno?
  2. Demostralo. Con el CRUD andando, editá la regla del puerto 8888 para que permita solo la IP 203.0.113.10/32 (una IP reservada para ejemplos, que no es la tuya), y sacá una captura del navegador cuando intentás entrar al CRUD. Después volvé a dejar la regla en Mi IP (My IP) y comprobá que vuelve a andar. ¿Por qué el navegador se queda esperando hasta dar timeout en lugar de mostrar enseguida "conexión rechazada"?

Paso 11 — Apagar todo

Una instancia prendida consume crédito aunque no la estés usando.

  1. En EC2 → Instancias (Instances), seleccioná tu instancia → Estado de la instancia (Instance state) → Detener instancia (Stop instance).
  2. En el panel del Learner Lab, hacé clic en End Lab.

Si te olvidás, el Learner Lab detiene las instancias solo cuando se terminan las 4 horas de sesión, y las vuelve a arrancar la próxima vez que hagas Start Lab.

Si la volvés a prender otro día:

  • La IP pública cambia cada vez que la instancia se detiene y arranca: usá la nueva.
  • Los contenedores vuelven solos (restart: always), la base alumnos sigue ahí y el swap también.
  • El CRUD no vuelve solo: repetí el Paso 10 desde cd ~/practica (la IP del contenedor puede cambiar).
  • Si estás en otra red, actualizá Mi IP en el security group.

Para borrarla del todo (cuando el docente lo indique): Estado de la instancia → Terminar instancia (Instance state → Terminate instance). Se pierde todo lo que tenía.

Revisión final

Hiciste lo mismo que en Killercoda, pero además:

  1. Recorriste una VPC real: subredes, Internet gateway y tabla de rutas.
  2. Configuraste un firewall (security group) abriendo solo los puertos necesarios y solo para tu IP.
  3. Creaste un servidor a partir de una AMI, eligiendo tipo de instancia, disco y red.
  4. Te conectaste por SSH o desde el navegador.
  5. Instalaste Docker y levantaste MySQL, phpMyAdmin, Nginx y una app Flask.
  6. Viste las diferencias entre IP pública, IP privada de la VPC e IP de la red de Docker.

Tarea extra: el CRUD con login

El Learner Lab queda disponible hasta el 31/12. Esta tarea se hace otro día, con la misma instancia: es la continuación de la práctica.

En Killercoda, la práctica crud-auth-login le sumaba al CRUD una pantalla de login con sesiones. Si no la hiciste, o no te acordás, revisala antes de empezar. Acá vas a desplegar ese mismo login en tu servidor de AWS, desde la branch feature-login-aws del repo crud-python.

  1. Prendé el lab y la instancia, y conectate (Pasos 1 y 5). Recordá: la IP pública es otra, y si estás en otra red, actualizá Mi IP en el security group.

  2. En phpMyAdmin, entrá a la base alumnos → pestaña SQL, y creá la tabla de usuarios:

    USE alumnos;

CREATE TABLE usuarios (
  id INT PRIMARY KEY AUTO_INCREMENT,
  usuario VARCHAR(50) NOT NULL UNIQUE,
  password VARCHAR(50) NOT NULL
);

INSERT INTO usuarios (usuario, password) VALUES ('admin', 'admin123');

  3. En la terminal de la instancia, cambiá el CRUD a la branch con login. El git restore descarta el cambio que hizo el sed en app.py (si no, Git no te deja cambiar de branch); por eso después se repite el sed:

    pkill -f "python3 app.py"
cd ~/crud-python
git restore app.py
git fetch
git switch feature-login-aws
