Dimensionamiento de Servidores

Cuánto pesa lo que tu servidor entrega — y por qué importa

Esta unidad son 3 clases: hoy la teoría con datos reales, después una práctica guiada en Killercoda, y por último rediseñamos entre todos la Calculadora de Infraestructura para que use estos números en vez de valores inventados.

Dos formas de responder "iniciá sesión"

🖥️ Aplicación web completa

El servidor arma la página entera (HTML + estilos + interactividad) y la manda lista para mostrarse. Estilo Symfony/Twig, WordPress, Django templates.

🔌 Backend que solo da datos

El servidor solo contesta con los datos en JSON. La pantalla ya está en el navegador o en la app — sólo necesita saber si el login fue válido.

Misma acción del usuario, dos respuestas completamente distintas en tamaño. ¿Cuánto es "distintas"? Vamos a medirlo con casos reales, no inventados.

Medición real #1: una página de login completa

Caso real: la página de inicio de sesión de WordPress.com (aplicación de producción, renderizada en el servidor).

MedidaTamaño
HTML tal cual lo arma el servidor155.332 bytes (~152 KB)
Lo que realmente viaja por la red (comprimido, gzip)61.016 bytes (~59,6 KB)
curl -sL -H "Accept-Encoding: gzip" -o /dev/null -w "%{size_download} bytes\n" \ https://wordpress.com/log-in

Medido el 07/08/2026. Incluso comprimido, es una sola respuesta HTTP con toda la página lista para pintar.

Medición real #2: un JSON de login

Dos APIs públicas reales de prueba, mismo tipo de operación (POST de login):

APIQué devuelveTamaño real
fakestoreapi.com/auth/loginSolo el token152 bytes
dummyjson.com/auth/loginToken + refresh token + datos del usuario930 bytes
curl -s -X POST https://dummyjson.com/auth/login \ -H "Content-Type: application/json" \ -d '{"username":"emilys","password":"emilyspass"}' \ -w "\nbytes: %{size_download}\n"

Medido el 07/08/2026. Vamos a usar 930 bytes como referencia "realista" (incluye datos de usuario, no solo el token).

La comparación, cara a cara

Página completa (gzip)
61 KB
JSON de login
930 B

La página completa pesa ~65 veces más que el JSON. Contra la versión mínima (152 B, solo token), la diferencia es de ~400 veces.

¿Por qué pesa tanto la página completa?

  • Trae el HTML con toda la estructura y el contenido ya insertado
  • Trae (o referencia) el CSS del framework visual completo, aunque la página use una fracción de esas reglas
  • Trae el JavaScript necesario para que la página sea interactiva
  • El servidor tiene que renderizar la plantilla (Twig, Blade, etc.) en cada request — no es gratis en CPU

¿Por qué el JSON pesa tan poco?

  • Solo viajan datos: token, id de usuario, algún campo más
  • No hay presentación — el HTML/CSS/JS ya está en el cliente (la app o la SPA), se descargó una sola vez
  • Serializar un objeto a JSON es una operación mucho más liviana que renderizar una plantilla completa

El ahorro no es solo de red: también es de CPU del servidor, que ya no arma HTML en cada pedido.

Escalando: de 10 a 10.000 logins

Multiplicando cada respuesta por la cantidad de usuarios que inician sesión:

10610 KB9,3 KB
1006,1 MB93 KB
1.00061 MB0,9 MB
10.000610 MB9,3 MB

Sin contar recompresión ni caché — es el volumen de datos que el servidor tiene que generar y transmitir.

De bytes a ancho de banda

Si esos 10.000 logins ocurren en una ventana corta y realista — por ejemplo, todos entran en los primeros 10 segundos (arranque de clase, apertura de un examen, inicio de una inscripción):

Página completa
~488Mbps necesarios
JSON
~7,4Mbps necesarios

610 MB ÷ 10 s = 61 MB/s ≈ 488 Mbps. Con JSON, 9,3 MB ÷ 10 s ≈ 7,4 Mbps. Esta es la diferencia real entre dimensionar un enlace de red "grande" o uno modesto.

Usuarios registrados ≠ peticiones simultáneas

No todos los usuarios registrados usan el sistema al mismo tiempo. Reglas prácticas aproximadas (no son leyes fijas):

  • Uso distribuido en el día (red social, e-commerce): el pico concurrente suele rondar el 5-15% de los usuarios activos
  • Uso sincronizado (examen, asistencia, apertura de inscripción): el pico puede acercarse al 80-100% en una ventana de segundos o minutos

Para dimensionar un servidor hay que diseñar para el peor escenario realista, no para el promedio. Un sistema de asistencia donde 30 alumnos entran en el mismo minuto es, en la práctica, un caso de uso sincronizado.

Una sesión no es una sola petición

El login es apenas el arranque. Una sesión real sigue generando tráfico después:

Aplicación completa (MPA)

Cada navegación = una página nueva completa. Menos peticiones, pero cada una pesa mucho.

SPA / API

Muchas peticiones chicas: cada clic, cada refresco de token, cada dato que cambia. Más peticiones, pero cada una pesa muy poco.

Por eso "usuarios" no se traduce directo a "peticiones": hay que multiplicar por cuántas peticiones genera cada usuario activo por minuto, y esa cifra depende de la arquitectura elegida.

Conclusiones clave

  • La arquitectura (página completa vs. JSON) define el peso de cada respuesta — acá vimos una diferencia real de ~65x
  • Ese peso, multiplicado por la cantidad de usuarios, es lo que define el ancho de banda y la CPU que hay que dimensionar
  • Hay que dimensionar para el pico, no para el promedio — sobre todo si el uso tiende a sincronizarse
  • "Usuarios" y "peticiones" no son lo mismo: falta el factor de concurrencia y las peticiones por sesión
