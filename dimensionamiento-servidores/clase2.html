Esto es, literalmente, el Trabajo Práctico N°8 del programa: una propuesta de infraestructura para un sistema real, justificada como lo haría un Analista Funcional. Hoy lo practicamos con un caso de ejemplo; después lo hacen con el suyo.

Repaso relámpago — Clase 1

  • Una página completa (HTML+CSS+JS) puede pesar ~65 veces más que un JSON equivalente
  • Ese peso, multiplicado por la cantidad de usuarios, define ancho de banda y CPU
  • Hay que dimensionar para el pico, no para el promedio
  • Usuarios registrados ≠ usuarios concurrentes: importa cuántos entran al mismo tiempo

Hoy estas ideas dejan de ser teoría suelta: las convertimos en una fórmula que arranca de los Requisitos que ya escribieron para su proyecto EIDAS.

De Stakeholders y Requisitos a Infraestructura

En Desarrollo de Sistemas Web ya escribieron, para su propio proyecto:

  • Stakeholders: quiénes usan el sistema y con qué frecuencia
  • Requisitos funcionales: qué hace el sistema
  • Requisitos no funcionales (si ya llegaron): qué tan rápido, qué tan disponible, cuánta gente al mismo tiempo

Todo eso son datos de entrada para dimensionar un servidor. Un Analista Funcional no adivina la infraestructura: la deriva de lo que ya relevó.

El menú de decisiones (Unidad 8)

¿Dónde vive el servidor?

  • Servidor físico propio (on-premise)
  • Servidor virtual (VM)
  • Contenedor
  • Cloud: IaaS / PaaS / SaaS

¿Con qué garantías?

  • Alta disponibilidad y redundancia
  • Backup y recuperación ante desastres
  • Nivel de uptime prometido (SLA)

Estas decisiones no son técnicas puras: dependen de qué tan crítico es el sistema y de cuánto presupuesto hay. Eso también sale de los Stakeholders.

Nube vs. Servidor Propio — Ventajas y Desventajas

☁️ Cloud (IaaS/PaaS)

Ventajas

  • Costo inicial bajo — pagás por uso
  • Se implementa en minutos, no semanas
  • Escala automáticamente ante picos
  • El proveedor hace el mantenimiento
  • Disponible en múltiples regiones

Desventajas

  • Costo recurrente que puede crecer sin control
  • Menos control físico sobre los datos
  • Depende de la conectividad a internet

🏢 On-Premise

Ventajas

  • Costo fijo, se amortiza con el tiempo
  • Control total y físico de los datos
  • Más simple de auditar para normativas estrictas
  • No depende de un proveedor externo

Desventajas

  • Costo inicial alto — hay que comprar el hardware
  • Semanas de implementación (compra + instalación)
  • Escalar significa comprar más equipo
  • Necesita un equipo propio de IT para mantenerlo

¿Cuál conviene, según tus requisitos?

Si tu sistema tiene este requisito......conviene
Presupuesto inicial muy ajustado☁️ Cloud
No sabés cuántos usuarios vas a tener, puede crecer rápido☁️ Cloud
No hay equipo de IT propio para mantener hardware☁️ Cloud
Datos extremadamente sensibles con normativa muy estricta🏢 On-Premise
Uso estable y predecible durante años, presupuesto para comprar equipo🏢 On-Premise
Ya existe infraestructura y personal de IT en la organización🏢 On-Premise

No hay una respuesta correcta universal: se decide cruzando cada requisito no funcional con estas ventajas y desventajas, no de memoria. Eso es lo que vamos a hacer ahora con un caso concreto.

Paso 1: ¿Cuántos usuarios al mismo tiempo?

La fórmula de Usuarios Concurrentes (CCU):

CCU = (Usuarios totales × % activos diarios × % concurrentes) × Factor de pico
Tipo de sistemaFactor de pico
Sistema médico / turnos1.2 – 1.5
E-commerce2.0 – 4.0
Educación (exámenes, inscripciones)3.0 – 5.0
Gobierno / trámites1.3 – 1.8

Fuente: Guía de Estimación de Infraestructura en la Nube (recurso de la materia).

Paso 2: De usuarios concurrentes a CPU y RAM

Tipo de aplicaciónRecursos por bloque de usuarios concurrentes
Sitio web estático1 vCPU, 1 GB RAM cada 100 usuarios
Aplicación web dinámica2 vCPU, 4 GB RAM cada 50 usuarios
Sistema transaccional4 vCPU, 8 GB RAM cada 25 usuarios
Sistema en tiempo real8 vCPU, 16 GB RAM cada 10 usuarios

La mayoría de los proyectos EIDAS son aplicaciones web dinámicas o sistemas transaccionales (dan de alta, modifican y consultan datos). Ahí es donde va a caer casi todo el curso.

Paso 3: ¿Cuánto storage necesita?

Usuario básico ......... 1-5 KB Transacción ............ 0.5-2 KB Imagen pequeña ......... 100-500 KB Documento .............. 1-10 MB + Backup automático ..... 100% adicional + Logs del sistema ...... 10-20% del storage total + Factor de crecimiento . 2-3x anual

Regla práctica: calculá el storage del primer año y después duplicalo o triplicalo para no quedarte corto a mitad del segundo.

🧮 Caso resuelto en vivo

Ejemplo: Sistema de Turnos — un consultorio con varios profesionales que gestiona reservas online.

Los números son de ejemplo, para mostrar el método. Después lo repiten con los datos reales de su propio proyecto.

El caso: Sistema de Turnos

Contexto

  • 1 consultorio, 8 profesionales
  • 1.200 pacientes registrados
  • Reservan turnos y ven su historial
  • Uso normal + picos los lunes a la mañana

Requisitos no funcionales

  • RNF1: Disponibilidad 99.5% en horario de atención
  • RNF2: Respuesta de reserva en menos de 2 segundos
  • RNF3: Backup diario de la base de datos

1Calculamos usuarios concurrentes

1.200 usuarios registrados × 20% activos diarios = 240 × 15% concurrentes = 36 × 1.4 factor de pico (turnos, similar a médico) = ~50 CCU

CCU estimado: ~50 usuarios concurrentes en el pico del lunes a la mañana.

2Elegimos CPU, RAM y storage

Es una aplicación web dinámica con lógica de negocio (turnos, disponibilidad, historial) → sistema transaccional: 4 vCPU / 8 GB RAM cada 25 CCU.

50 CCU ÷ 25 CCU por bloque = 2 bloques 2 × (4 vCPU, 8 GB RAM) = 8 vCPU, 16 GB RAM

Storage: 1.200 usuarios + historial de turnos (transacciones chicas) ronda un par de GB el primer año. Con backup diario (+100%) y margen de crecimiento, 50 GB SSD es un punto de partida cómodo.

3¿Nube o servidor propio?

Cruzamos el contexto del consultorio contra la guía de decisión:

  • Sin equipo de IT propio → pesa a favor de Cloud (ventaja: mantenimiento lo hace el proveedor)
  • Presupuesto ajustado, sin margen para comprar hardware → Cloud (ventaja: costo inicial bajo)
  • RNF1 pide 99.5% de disponibilidad → Cloud lo ofrece de fábrica; on-premise lo tendría que construir
  • Datos de salud → hay que revisar certificaciones del proveedor (la desventaja de Cloud a vigilar), pero no exige on-premise por sí solo

Tres de cuatro requisitos empujan a Cloud (VPS o IaaS), y el cuarto es manejable con un buen proveedor. Esa es la justificación — no "porque sí es más moderno".
