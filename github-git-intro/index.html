¿Qué es el control de versiones?

Un sistema que registra los cambios en tus archivos a lo largo del tiempo, para poder volver atrás, comparar y colaborar sin pisarse el trabajo.

🕒

Historial completo

Cada cambio queda guardado — sabés qué se modificó, cuándo y por qué.

⏪

Volver atrás

Si algo se rompe, podés recuperar una versión anterior del código.

👥

Trabajo en equipo

Varias personas editan el mismo proyecto sin sobrescribirse entre sí.

🌿

Ramas (branches)

Probás cosas nuevas en paralelo, sin tocar la versión estable.

Git es la herramienta más usada del mundo para esto.

Git vs GitHub

No son lo mismo

⚙️

Git

Un programa que corre en tu computadora. Lleva el historial de versiones de tu proyecto de forma local, sin necesitar Internet.

☁️

GitHub

Una plataforma web que hostea repositorios de Git en la nube. Permite compartir código, colaborar y hacer backup remoto.

Git es la herramienta. GitHub es uno de los lugares donde alojás ese repositorio (también existen GitLab, Bitbucket, etc.).

Las tres áreas de Git

Todo archivo pasa por estas etapas antes de quedar guardado en el historial.

📁Working Directory tus archivos, editando
→git add
📋Staging Area listos para guardar
→git commit
📦Repositorio local guardados en el historial

git add elige qué cambios van al próximo commit. git commit los guarda en el historial de forma permanente.

📦 Commit

Una foto del estado de tus archivos en un momento dado, con un mensaje que explica qué cambió.

✍️

Mensaje claro

Describe el qué y el por qué del cambio, no cada línea modificada.

🧩

Commits pequeños

Mejor varios commits chicos y enfocados que uno gigante con todo mezclado.

🆔

Identificador único

Cada commit tiene un hash (ej: 897609f) que lo identifica para siempre.

Ejemplo:

git commit -m "Agregar validación de formulario de login"

Repositorio local vs remoto

💻Tu computadora repositorio local
⇄
☁️GitHub repositorio remoto

Tenés una copia completa del historial en tu máquina, y otra copia en GitHub (el remoto).

Para mantenerlas sincronizadas usamos dos comandos: push y pull.

⬆️ Push

Envía tus commits locales al repositorio remoto en GitHub.

💻Local tenés commits nuevos
→git push
☁️GitHub recibe los commits

git push origin main

Lo usás cuando terminaste de trabajar y querés que tus cambios queden disponibles para el resto del equipo (o como backup).

⬇️ Pull

Trae los cambios del remoto y los combina con tu copia local.

☁️GitHub tiene commits nuevos
→git pull
💻Local se actualiza

git pull origin main

git pull = git fetch (descarga los cambios) + git merge (los une a tu rama). Hacelo antes de empezar a trabajar, para no quedar desactualizado.

El flujo completo

1
git pull — traés los últimos cambios del remoto antes de empezar.
2
Editás tus archivos en el working directory.
3
git add archivo — mandás los cambios al staging area.
4
git commit -m "mensaje" — guardás una foto en el historial local.
5
git push — subís tus commits al repositorio remoto en GitHub.

Este ciclo se repite todo el tiempo mientras trabajás en un proyecto.

Buenas prácticas

✅

Pull antes de empezar

Evita conflictos por trabajar sobre una versión desactualizada.

✍️

Mensajes de commit claros

"Fix bug" no ayuda a nadie — describí qué se corrigió y por qué.

🧩

Commits chicos y frecuentes

Más fácil de revisar, entender y revertir si algo sale mal.

🔍

git status es tu amigo

Revisá siempre qué vas a subir antes de hacer commit o push.
