📋 Requisitos

La diferencia entre un requisito que se puede verificar y uno que solo suena bien

RF vs. RNF: la pregunta que responde cada uno

🎯

Requisito Funcional (RF)

Responde "¿qué hace el sistema?" — un comportamiento observable: crear un pedido, asignar un repartidor, generar un reporte.

⚡

Requisito No Funcional (RNF)

Responde "¿cómo lo hace?" — una cualidad medible: qué tan rápido, qué tan seguro, cuánta carga soporta.

Mezclar los dos en la misma lista es el error más común: "el sistema debe procesar pagos de forma segura y rápida" mete un RF (procesar pagos) y dos RNF (seguridad, performance) en una sola frase.

Un RNF vago vs. uno medible

❌ Vago
"El sistema debe ser rápido y fácil de usar."

No se puede verificar. ¿Rápido comparado con qué? ¿Fácil según quién? Nadie puede decir si esto se cumplió o no.

✅ Medible
"Tiempo de respuesta < 2 segundos. Soporte para 500 usuarios concurrentes por sucursal. Tiempo de aprendizaje < 15 minutos para un usuario nuevo."

Cada número es un criterio de aceptación: se puede medir y decir con certeza si el sistema lo cumple.

Un RF vago vs. uno observable

❌ Vago
"El sistema debe gestionar bien los pedidos."

"Gestionar bien" no es un comportamiento — es una intención. No dice qué acciones puede hacer un usuario.

✅ Observable
"El sistema permite crear, modificar y cancelar un pedido, con seguimiento en tiempo real y estimación del tiempo de entrega."

Cada verbo es algo que un usuario puede hacer y que se puede probar directamente.

El caso: Sistema de Pedidos a Domicilio

Agrupados por módulo, con ID — así se espera el archivo requisitos.md.

Requisitos Funcionales
RF01 Gestión de Pedidos — crear, modificar, cancelar; seguimiento en tiempo real
RF04 Gestión de Entregas — asignación automática de repartidor, tracking GPS
RF05 Gestión de Pagos — múltiples métodos, procesamiento seguro

Requisitos No Funcionales
RNF01 Performance — respuesta < 2s, 500 usuarios concurrentes por sucursal
RNF03 Seguridad — cumplimiento PCI DSS para pagos (lo exige el stakeholder "procesador de pagos")
RNF05 Escalabilidad — fácil incorporación de nuevas sucursales

Notá la coherencia con Stakeholders: RNF03 no es un capricho técnico — existe porque el procesador de pagos (sistema externo) lo exige. Eso es justamente lo que la rúbrica llama "coherencia con el caso".

Qué mira la rúbrica (15 puntos)

Muy bueno (13-15)

Agrupados por módulo con IDs claros. Los RF describen comportamiento observable, no intenciones. Los RNF tienen valores medibles. Hay coherencia entre los RF y el caso de estudio.

Bueno (10-12)

Presentes y agrupados. La mayoría son observables y medibles, pero alguno queda vago o genérico.

Regular (6-9)

Incompletos o mezclados sin distinguir RF de RNF. Predominan enunciados genéricos ("el sistema debe ser rápido") sin valores concretos.

Insuficiente (0-5)

Faltan requisitos relevantes para el caso, o los presentes describen características deseables sin especificación real.

Antes de dar por cerrado el archivo

  • ¿Cada RF describe algo que el usuario puede hacer, no una intención genérica?
  • ¿Cada RNF tiene un número o valor concreto (tiempo, porcentaje, cantidad)?
  • ¿Los RF están agrupados por módulo, con ID (RF01, RF02...)?
  • ¿Cada requisito se conecta con algo real del caso de estudio (no serviría igual para cualquier sistema)?
