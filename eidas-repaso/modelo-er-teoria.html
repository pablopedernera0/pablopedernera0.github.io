Modelo Entidad-Relación

Cómo pasar de "sé qué tiene que hacer el sistema" a "sé qué datos hay que guardar y cómo se conectan". El modelo ER es el plano de la base de datos antes de escribir una sola tabla.

1Dónde encaja el ER en el proceso

El modelo ER no se inventa de la nada ni es el primer paso. Llega después de saber qué hace el sistema y antes de crear la base de datos real:

Requisitos + HUqué necesita el sistema
Casos de Usoquién hace qué y con qué datos
Modelo ERqué se guarda y cómo se relaciona
Modelo relacionaltablas, columnas, claves
Base de datosel CREATE TABLE real

Regla de oro que vamos a repetir toda la clase: cada entidad y cada atributo del ER tiene que poder rastrearse hasta un requisito o un caso de uso. Si aparece algo que nadie pidió, sobra. Si un CU necesita un dato que no está, falta.

2Los tres bloques del modelo

Un modelo ER se arma con solo tres piezas. Todo lo demás son detalles de esas tres:

Entidades

Las "cosas" de las que el sistema guarda información: un cliente, un producto, un préstamo. Se dibujan como rectángulos.

Atributos

Los datos concretos de cada entidad: el nombre del cliente, el precio del producto, la fecha del préstamo.

Relaciones

Cómo se conectan las entidades entre sí: un cliente realiza pedidos, un socio toma prestado un libro.

3Entidades

Una entidad es una clase de objeto sobre el que guardamos datos. Ojo con la diferencia clave:

  • Entidad = el tipo, el molde. Ejemplo: CLIENTE.
  • Instancia = un caso concreto de ese molde. Ejemplo: el cliente "Ana Gómez, DNI 30.111.222".

En el modelo dibujamos la entidad (el molde) una sola vez, aunque después la base tenga miles de instancias.

Entidad fuerte y entidad débil

Una entidad fuerte existe por sí sola y tiene su propio identificador (un CLIENTE existe sin depender de nadie). Una entidad débil no puede identificarse sola: depende de otra para tener sentido. Ejemplo típico: un DETALLE_PEDIDO no existe sin su PEDIDO; una CUOTA no existe sin su CREDITO.

4Atributos

Los atributos son los datos de cada entidad. No todos son iguales, y distinguirlos evita errores clásicos:

TipoQué esEjemplo
SimpleUn solo valor indivisible.precio, dni
CompuestoSe puede descomponer en partes.direccion → calle, número, ciudad
MultivaluadoPuede tener varios valores para una misma instancia.telefonos de un cliente
DerivadoSe calcula a partir de otros; no se guarda "crudo".edad (se deriva de la fecha de nacimiento)
ClaveIdentifica de forma única cada instancia.cliente_id

Dos trampas frecuentes: guardar un dato derivado como si fuera fijo (guardar la edad en vez de calcularla — al día siguiente ya está mal), y meter un atributo multivaluado como una sola columna (un campo "teléfonos" con tres números separados por comas es un problema, no una solución: eso pide una entidad aparte).

5Claves: PK, candidata y FK

Clave primaria (PK)

El atributo (o combinación) que identifica de forma única cada instancia. No se repite y no puede quedar vacío. Cada entidad tiene exactamente una PK.

Clave candidata

Cualquier atributo que también podría servir de identificador único. De todas las candidatas se elige una como PK; el resto quedan como alternativas.

Clave foránea (FK)

Un atributo que apunta a la PK de otra entidad. Es el mecanismo con el que se materializa una relación en los datos.

Notación que vamos a usar en el pizarrón y en el archivo: la PK subrayada, la FK marcada con FK.

6Relaciones y cardinalidad

Una relación conecta dos entidades. Lo importante no es solo que estén conectadas, sino cuántas instancias de una se conectan con cuántas de la otra. Eso es la cardinalidad:

CardinalidadSignificadoEjemplo
1 : 1Una instancia de A se relaciona con una sola de B, y viceversa.Un PEDIDO tiene un solo PAGO.
1 : NUna instancia de A se relaciona con muchas de B, pero cada B con una sola A.Un CLIENTE realiza muchos PEDIDO; cada pedido es de un solo cliente.
N : MMuchas de A con muchas de B, en ambos sentidos.Un LIBRO lo escriben varios AUTOR; un autor escribe varios libros.

Participación total o parcial

Además de "cuántos", importa "¿es obligatorio?". Si toda instancia de una entidad tiene que participar en la relación, la participación es total (un DETALLE_PEDIDO siempre pertenece a un pedido). Si puede no participar, es parcial (un CLIENTE puede existir sin haber hecho ningún pedido todavía).

7El caso especial N:M

Una relación muchos-a-muchos no se puede implementar directamente en una base relacional: ¿dónde pondrías la FK, si de los dos lados hay "muchos"? Se resuelve creando una entidad intermedia (o entidad asociativa) que parte el N:M en dos relaciones 1:N:

Antes (no se puede implementar así):
  LIBRO N --- M AUTOR

Después (entidad intermedia AUTORIA):
  LIBRO 1 --- N AUTORIA N --- 1 AUTOR

La entidad intermedia además es el lugar natural para los datos de la relación misma: en un DETALLE_PEDIDO viven la cantidad y el subtotal, que no son ni del pedido ni del producto por separado, sino del cruce entre ambos.

8Caso resuelto paso a paso

Enunciado corto de ejemplo:

"Una biblioteca registra sus socios y sus libros. Un socio puede pedir prestados varios libros a lo largo del tiempo, y cada libro puede ser prestado a muchos socios (en distintas fechas). De cada préstamo interesa la fecha en que se retiró y la fecha de devolución. Cada libro fue escrito por uno o más autores."

  1. Detectar las entidades — los sustantivos importantes que hay que guardar: SOCIO, LIBRO, AUTOR. "Préstamo" también es un candidato: guárdenlo en el radar.
  2. Detectar las relaciones — los verbos: un socio pide prestado un libro; un libro fue escrito por autores.
  3. Poner cardinalidades — "un socio pide varios libros y un libro va a muchos socios" → N:M. "un libro lo escriben uno o más autores y un autor escribe varios" → N:M. Dos muchos-a-muchos.
  4. Resolver los N:M — el préstamo socio-libro se vuelve la entidad PRESTAMO (que además guarda fecha_retiro y fecha_devolucion, datos de la relación). El libro-autor se vuelve AUTORIA.
  5. Asignar atributos y claves — cada entidad recibe su PK y sus datos; las intermedias reciben las FK a las dos entidades que cruzan.

Modelo resultante:

SOCIO(socio_id, nombre, email)
LIBRO(libro_id, titulo, anio, isbn)
AUTOR(autor_id, nombre)
PRESTAMO(prestamo_id, socio_id FK, libro_id FK, fecha_retiro, fecha_devolucion)
AUTORIA(autoria_id, libro_id FK, autor_id FK)

SOCIO 1 --- N PRESTAMO N --- 1 LIBRO
LIBRO 1 --- N AUTORIA N --- 1 AUTOR

9Del ER al modelo relacional (adelanto)

El ER es el plano; el modelo relacional es la obra. La traducción sigue reglas mecánicas que vemos en detalle más adelante, pero la idea básica ya se puede anticipar:

  • Cada entidad se vuelve una tabla; cada atributo, una columna.
  • La PK de la entidad es la PK de la tabla.
  • Una relación 1:N se implementa poniendo la FK del lado "1" en la tabla del lado "N".
  • Una relación N:M ya la resolvimos en el ER con una entidad intermedia, así que se traduce como cualquier tabla, con dos FK.

10Errores comunes (para revisar antes de entregar)

  • Entidades que nadie pidió (no rastreables a un RF/CU) o que faltan aunque un CU las necesite.
  • Dejar un N:M sin resolver: en una base relacional no se puede implementar así.
  • Meter un atributo multivaluado (varios teléfonos, varias categorías) como una sola columna con comas.
  • Guardar un dato derivado (edad, total) como si fuera fijo, en vez de calcularlo.
  • Marcar la línea de relación pero no la cardinalidad (1:1 / 1:N / N:M): media relación no dice nada.
  • Poner una decisión de diseño enunciada ("agregamos la entidad X") sin justificarla (por qué, y qué alternativa se descartó).
