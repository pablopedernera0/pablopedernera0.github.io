Ya vimos qué son S3 e IAM — hoy vamos un nivel más profundo, con ejemplos reales por consola web y por línea de comandos.

Repaso relámpago

💾

S3

Almacenamiento de objetos: archivos organizados en buckets, cada uno identificado por una key única.

🔐

IAM

Control de acceso: define quién puede hacer qué sobre qué recurso de AWS.

Esto ya lo vimos en la clase anterior. Hoy: cada operación explicada y ejecutada, dos veces — una desde el navegador y otra desde la terminal.

💾 S3: conceptos clave

🪣

Bucket

Contenedor de nivel superior. Su nombre debe ser único a nivel global en todo AWS.

📄

Object

El archivo más sus metadatos. Desde bytes hasta 5 TB por objeto.

🔑

Key

Identificador único del objeto dentro del bucket. No existen carpetas reales: todo es una key con forma de ruta.

🌎

Región

Cada bucket vive en una región específica (ej. sa-east-1), elegida al crearlo.

🔁

Versionado

Opcional: conserva versiones anteriores del mismo objeto ante sobrescrituras o borrados.

📛

Reglas de nombre

Minúsculas, 3 a 63 caracteres, sin espacios ni mayúsculas, único en todo AWS.

S3 por consola web: crear un bucket

  1. Entrar a la consola de AWS y buscar el servicio S3.
  2. Click en Create bucket.
  3. Elegir un nombre único (ej. fotos-alumnos-2026) y la región.
  4. Dejar bloqueado el acceso público por defecto, salvo que el bucket lo necesite explícitamente.
  5. Click en Create bucket para confirmar.

El nombre queda reservado en todo AWS mientras exista el bucket — por eso conviene sumar un sufijo propio (año, curso, etc.).

S3 por consola web: subir, descargar, borrar

  1. Entrar al bucket y click en Upload.
  2. Arrastrar el archivo o usar Add files, luego Upload para confirmar.
  3. Click sobre el objeto para ver su detalle, y Download para descargarlo.
  4. Seleccionar el objeto (checkbox) y Delete para eliminarlo.

Cada objeto puede tener una URL pública o firmada, según los permisos del bucket y del objeto.

Antes de usar la CLI

Instalamos AWS CLI y la configuramos una vez con nuestras credenciales.

$ aws configure
AWS Access Key ID [None]: AKIAEXAMPLE123
AWS Secret Access Key [None]: ****************
Default region name [None]: sa-east-1
Default output format [None]: json

Como estamos contra Floci (emulador) y no AWS real, agregamos --endpoint-url http://localhost:4566 a cada comando — o lo exportamos una sola vez como variable de entorno.

S3 por CLI: crear y subir

$ aws s3 mb s3://fotos-alumnos-2026 --endpoint-url http://localhost:4566
make_bucket: fotos-alumnos-2026
 
$ aws s3 cp foto.jpg s3://fotos-alumnos-2026/ --endpoint-url http://localhost:4566
upload: ./foto.jpg to s3://fotos-alumnos-2026/foto.jpg
 
$ aws s3 ls s3://fotos-alumnos-2026 --endpoint-url http://localhost:4566
2026-08-06 10:15:32 245678 foto.jpg

S3 por CLI: descargar y borrar

$ aws s3 cp s3://fotos-alumnos-2026/foto.jpg ./descarga.jpg --endpoint-url http://localhost:4566
download: s3://fotos-alumnos-2026/foto.jpg to ./descarga.jpg
 
$ aws s3 rm s3://fotos-alumnos-2026/foto.jpg --endpoint-url http://localhost:4566
delete: s3://fotos-alumnos-2026/foto.jpg
 
$ aws s3 rb s3://fotos-alumnos-2026 --endpoint-url http://localhost:4566
remove_bucket: fotos-alumnos-2026

El mismo ciclo CRUD que hicimos con clicks en la consola — pero scripteable y repetible.

🔐 IAM: conceptos clave

👤

Usuarios

Identidad individual — persona o aplicación — con credenciales propias.

👥

Grupos

Conjunto de usuarios que comparten permisos. La policy se adjunta al grupo, no a cada usuario.

🎭

Roles

Identidad temporal, sin credenciales fijas, que puede asumir un usuario o un servicio.

📜

Policies

Documento JSON que define qué acciones están permitidas o denegadas sobre qué recursos.

🔑

Access Keys

AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY — credenciales que usa una app para autenticarse.

🎯

Mínimo privilegio

Dar solo los permisos estrictamente necesarios para la tarea, ni uno más.

IAM por consola web

  1. IAM → Users → Create user (ej. alumno-app).
  2. IAM → User groups → Create group (ej. app-s3-access) y agregar al usuario.
  3. Adjuntar una policy al grupo (managed o custom en JSON).
  4. Entrar al usuario → Security credentials → Create access key.
  5. Guardar el Access Key ID y el Secret Access Key — solo se muestran una vez.

IAM por CLI: usuarios y grupos

$ aws iam create-user --user-name alumno-app --endpoint-url http://localhost:4566
 
$ aws iam create-group --group-name app-s3-access --endpoint-url http://localhost:4566
 
$ aws iam add-user-to-group --user-name alumno-app \
--group-name app-s3-access --endpoint-url http://localhost:4566

IAM por CLI: policy y access key

policy.json — acceso solo al bucket fotos-alumnos-2026:

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"], "Resource": [ "arn:aws:s3:::fotos-alumnos-2026", "arn:aws:s3:::fotos-alumnos-2026/*" ] } ] }
$ aws iam put-group-policy --group-name app-s3-access \
--policy-name s3-fotos-access --policy-document file://policy.json --endpoint-url http://localhost:4566
 
$ aws iam create-access-key --user-name alumno-app --endpoint-url http://localhost:4566
{ "AccessKey": { "UserName": "alumno-app", "AccessKeyId": "AKIA...", "SecretAccessKey": "..." } }

Consola web vs CLI: ¿cuándo usar cada una?

Consola webAWS CLI
Ideal paraExplorar, aprender, tareas puntualesAutomatizar, scripts, tareas repetidas
Velocidad (1 acción)Rápida, a base de clicksRequiere conocer el comando exacto
RepetibilidadManual cada vezScripteable y reproducible
TrazabilidadNo queda como códigoQueda como script versionable en git
Curva de aprendizajeBajaMedia — sintaxis de comandos

En la práctica real se usan las dos: la consola para explorar y entender, la CLI/SDK para las apps y la automatización.

Buenas prácticas de seguridad

🚫

No usar el usuario root

El root es solo para tareas de cuenta. Para trabajo diario, siempre usuarios IAM.

🔄

Rotar access keys

Generar nuevas periódicamente y desactivar/eliminar las que ya no se usan.

🙈

Nunca commitear credenciales

Las access keys no van en el código ni en git — se usan variables de entorno o un gestor de secretos.

🎯

Mínimo privilegio

Policies específicas por recurso, nunca AdministratorAccess para una app.
