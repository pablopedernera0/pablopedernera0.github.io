Hilo conductor de redes

Cuatro prácticas encadenadas sobre la misma infraestructura (Nginx + MySQL + PhpMyAdmin + una app Flask CRUD): se despliega, se mide, se ataca y se explota. Cada escenario es autocontenido — no depende de que el alumno haya dejado nada corriendo de la práctica anterior.

Nota ética

Repetir explícitamente en clase antes de las etapas 3 y 4.

Antes de atacar nada

  • Todo el ataque es contra infraestructura propia, desplegada por el alumno, dentro de su propio sandbox.
  • Las mismas técnicas contra un sistema ajeno, sin autorización explícita, son un delito.
  • El objetivo pedagógico es entender cómo piensa un atacante para defender mejor — no formar atacantes.

Logística general

Duración total de las 4 etapas: 45 + 35 + 45 + 45 = 170 min (~2h 50). No entra en una sola clase — conviene repartirlo en tres encuentros.

Por etapa

Etapa 1 crud-stress-test 45 min

Objetivos de aprendizaje

  • Explicar qué miden throughput, latencia, concurrencia y tasa de error
  • Usar ab contra un endpoint de lectura y uno de escritura, e interpretar la salida
  • Explicar por qué el servidor de desarrollo de Flask (single-threaded) se degrada bajo concurrencia
  • Levantar la misma app con Gunicorn y comparar métricas

Qué debería mostrar el alumno

  • ab -n 500 -c 20 contra GET /: throughput alto, cero fallos
  • El mismo test contra POST /nuevo con throughput menor
  • Fallos al forzar -c 200 contra el puerto 8888 (Flask dev server)
  • Mismo test contra el puerto 8889 (Gunicorn, 4 workers): más throughput, menos fallos

Resultados esperados

referencia rápida
alumnos sembrados: 5 $ ps aux | grep app.py # 1 proceso, puerto 8888 $ ps aux | grep gunicorn # master + 4 workers, puerto 8889
Etapa 2 crud-auth-login 35 min

Objetivos de aprendizaje

  • Diferenciar autenticación de autorización
  • Explicar qué es una sesión y por qué HTTP la necesita
  • Leer un @app.before_request y entender cómo protege rutas sin tocarlas una por una

Qué debería mostrar el alumno

  • curl -sI / sin cookie → 302 a /login
  • Login exitoso con admin / admin123, navegador y curl -c/-b
  • Identificar que la password se guarda en texto plano en usuarios

Resultados esperados

referencia rápida
usuario sembrado único: admin / admin123
Ética: no spoilear la vulnerabilidad todavía
Etapa 3 crud-ataques-red 45 min

Objetivos de aprendizaje

  • Diferenciar superficie de ataque externa (publicada al host) de interna (red Docker)
  • Encontrar credenciales hardcodeadas en código fuente y entender su impacto
  • Ejecutar fuerza bruta con hydra contra un formulario web

Qué debería mostrar el alumno

  • nmap -sV -p 80,8080,8888 localhost con los tres servicios identificados
  • nmap -p 3306 localhost cerrado, pero abierto contra la IP interna del contenedor
  • Conexión directa a MySQL con root / mysecretpassword
  • Resultado de hydra con la contraseña encontrada

Etapa 4 crud-sqli 45 min · puede extenderse

Objetivos de aprendizaje

  • Diferenciar una consulta parametrizada de una armada por concatenación/f-string
  • Ejecutar un bypass manual de autenticación por SQLi
  • Usar sqlmap para detectar y explotar automáticamente, y volcar una tabla

Qué debería mostrar el alumno

  • curl --data-urlencode "usuario=admin' -- " → 302 (bypass exitoso)
  • La variante ' OR '1'='1' -- funcionando sin conocer el usuario
  • sqlmap -p usuario --batch detectando el parámetro como inyectable
  • sqlmap ... --dump -D alumnos -T usuarios con el volcado completo

Resultados esperados — validado en un entorno real

alumnos.usuarios — sqlmap --dump
Database: alumnos Table: usuarios +----+---------+----------+ | id | usuario | password | +----+---------+----------+ | 1 | admin | admin123 | | 2 | soporte | sopor23! | +----+---------+----------+

En la corrida de validación, sqlmap detectó la inyección por time-based blind (no boolean-based): cada carácter implica varias peticiones con SLEEP, y el --dump completo tardó ~3-4 minutos. Avisar que es esperable que el comando "tarde en volver".

Ética: repetir la nota general — cerrar mostrando el fix (parametrizar), no dejar la app "rota para siempre"

Notas técnicas para quien mantenga estos escenarios

No es material para dar en clase.

  • Los cuatro setup.sh usan docker exec -i <container> mysql ... << 'EOSQL' — la flag -i es obligatoria; sin ella el heredoc no llega al contenedor y la tabla no se crea, en silencio. cloud-storage-101/assets/setup.sh (escenario más viejo) tiene este mismo bug sin corregir.
  • Las cuatro etapas clonan crud-python; las etapas 2-4 usan la branch feature-login, la etapa 1 usa main.
  • Credenciales de referencia usadas en todo el hilo: MySQL root/mysecretpassword; app admin/admin123 y soporte/sopor23! (esta última solo sembrada en crud-sqli, para que el --dump muestre más de una fila).
