El problema: cinco contenedores a mano

Sin Compose, nuestro stack se levanta así (resumido):

docker network create mynetwork

docker run -d --name mysql --restart always --network mynetwork \
  -e MYSQL_ROOT_PASSWORD=mysecretpassword mysql:latest

docker run -d --name dbexporter --restart always --network mynetwork \
  -v $(pwd)/my.cnf:/.my.cnf:ro prom/mysqld-exporter:latest --config.my-cnf=/.my.cnf

docker run -d --name cadvisor --restart always --network mynetwork \
  -v /:/rootfs:ro -v /var/run:/var/run:ro -v /sys:/sys:ro \
  -v /var/lib/docker/:/var/lib/docker:ro -v /dev/disk/:/dev/disk:ro \
  gcr.io/cadvisor/cadvisor:v0.47.2

docker run -d --name prometheus --restart always --network mynetwork -p 9090:9090 \
  -v $(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml \
  --add-host host.docker.internal:host-gateway prom/prometheus:latest

docker run -d --name grafana --restart always --network mynetwork -p 3000:3000 \
  -e GF_SECURITY_ADMIN_PASSWORD=admin grafana/grafana:13.2.2

¿Quién se acuerda de esto dentro de un mes? ¿En qué orden van? ¿Cómo se lo pasás a un compañero? ¿Cómo lo bajás todo?

La idea de Compose: describir, no ordenar

Imperativo

docker run: le das órdenes, una por una, en el orden correcto. El estado final queda en tu cabeza (o en tu historial de bash).

Declarativo

docker-compose.yml: describís cómo tiene que quedar todo. La herramienta calcula qué crear, en qué orden, y qué cambiar si editás el archivo.

Un archivo

Toda la infraestructura de la app en un solo lugar, legible.

Versionable

Va a Git como el código: hay historial, diffs y revisiones.

Un comando

up para levantar todo, down para bajarlo todo.

Es la misma idea que vamos a ver en Terraform o Kubernetes: se escribe la infraestructura como código.

Línea de tiempo

2013

Se publica Docker (marzo). A fin de año, la empresa Orchard publica Fig: un fig.yml para describir varios contenedores.

2014

Docker compra Orchard (julio). Fig se convierte en la herramienta oficial.

2015

Fig pasa a llamarse Docker Compose. Nace el docker-compose.yml (el formato que hoy llamamos "versión 1").

2016

Formato 2: aparecen version:, services:, networks: y volumes:.

2017

Formato 3: pensado también para Docker Swarm (clave deploy:).

2020

Compose Specification: un estándar abierto que unifica los formatos 2 y 3.

2022–23

Compose V2, reescrito en Go: el comando pasa a ser docker compose (con espacio). El viejo docker-compose (Python) deja de actualizarse.

Hoy

version: es obsoleta, el nombre preferido es compose.yaml, y siguen sumándose funciones.

2013–2015: Fig y el formato 1

# fig.yml (y después docker-compose.yml, formato 1)
web:
  build: .
  ports:
    - "5000:5000"
  links:
    - db
db:
  image: postgres

Qué tenía de particular

Los servicios iban directo en la raíz: no había services:, ni redes, ni volúmenes con nombre.

Para que web llegara a db había que declararlo con links:, que escribía la IP del otro contenedor en /etc/hosts.

Si en Internet encontrás un tutorial con links:, es de esta época. Hoy no hace falta: la red resuelve los nombres sola (lo vemos más adelante).

2016–2017: los formatos 2 y 3

Formato 2 · 2016

Aparece la estructura actual

Primera línea version: '2'. Los servicios pasan a vivir bajo services:, y se suman las claves de primer nivel networks: y volumes:. Cada proyecto tiene su propia red y los servicios se encuentran por nombre.

Formato 3 · 2017

Pensado para clusters

version: '3' agrega deploy: (réplicas y recursos) para usar el mismo archivo en Docker Swarm con docker stack deploy. A cambio, quitó opciones útiles en una sola máquina.

La confusión de esos años: el 3 no era "mejor" que el 2. Eran dos ramas para casos de uso distintos, y había que elegir. Nuestro archivo dice version: '3'.

2020 en adelante: un estándar y un comando nuevo

AntesHoy

docker-compose (con guion): un programa aparte, escrito en Pythondocker compose (con espacio): un plugin de Docker, escrito en Go

Dato real de nuestra práctica: el setup.sh instala el paquete docker-compose de apt (la versión 1, en Python) y el archivo arranca con version: '3'. Funciona, pero es un fósil: así se escribía en 2017.

YAML en diez minutos

YAML nació en 2001 como Yet Another Markup Language y después se rebautizó como YAML Ain't Markup Language: no es un lenguaje de marcado, es un formato de datos. Todo lo que hay en un archivo Compose es una combinación de tres cosas:

Mapa (clave: valor)

environment:
  MYSQL_ROOT_PASSWORD: mysecretpassword

Como un diccionario de Python o un objeto JSON.

Lista (guion)

networks:
  - mynetwork

Cada - es un elemento. Como un array.

Escalar

image: mysql:latest
restart: always

Texto, número, booleano o nulo.

La indentación define quién es hijo de quién. Se usan siempre espacios (por convención, 2), nunca tabs: YAML no los acepta para indentar.

Lo genera el setup.sh de la práctica en /root/monitoreo/. Vamos clave por clave.

image, restart y command

image

registro/usuario/nombre:etiqueta. Sin registro se usa Docker Hub; gcr.io/... es el de Google. La etiqueta latest cambia sola con el tiempo: por eso grafana está fijada en 13.2.2, para que la guía coincida con lo que ven en pantalla.

restart

Qué hace Docker si el contenedor se cae: no (por defecto), always, on-failure o unless-stopped. Con always también vuelve a arrancar cuando se reinicia la máquina.

command

Reemplaza el comando por defecto de la imagen. En dbexporter se pasa como lista: cada elemento es un argumento, y así no hay problemas con espacios ni comillas.

build (no aparece)

La alternativa a image: construir la imagen desde un Dockerfile. Es lo que van a usar en el Trabajo n°7 si dockerizan la app Flask.

environment: dos sintaxis en el mismo archivo

Como mapa · mysql 
environment:
  MYSQL_ROOT_PASSWORD: mysecretpassword

Clave y valor separados por :.

Como lista · grafana 
environment:
  - GF_SECURITY_ADMIN_PASSWORD=admin

Cada elemento es un texto VARIABLE=valor.

Las dos son válidas y hacen exactamente lo mismo. Que convivan en el mismo archivo es un buen ejemplo de por qué conviene elegir un estilo y respetarlo.

¿Por qué la contraseña va por variable de entorno? Porque la imagen oficial de MySQL la lee al arrancar por primera vez para crear el usuario root. Escribirla en el archivo, igual, la deja en Git a la vista de todos: hoy se usa un archivo .env que no se sube, o secrets:.

localhost:9090

Contenedor

prometheus:9090

donde escucha el proceso

Publicados

prometheus y grafana

Tienen ports: porque nosotros entramos desde el navegador.

Sin publicar

mysql, dbexporter, cadvisor

No tienen ports:. Prometheus llega igual a cadvisor:8080 porque están en la misma red. Desde afuera no se puede entrar.

Regla de seguridad: publicar solo lo que un humano (o algo fuera de Docker) necesita ver. La base de datos no se publica.

volumes: montar archivos y guardar datos

TipoEjemploPara qué
Bind mount (ruta del host)./prometheus.yml:/etc/prometheus/prometheus.ymlPasarle al contenedor un archivo de configuración que editamos nosotros
Bind mount de solo lectura./my.cnf:/.my.cnf:ro
/sys:/sys:ro		:ro = read only. El contenedor puede leer pero no modificar: cadvisor mira el host sin poder tocarlo
Volumen con nombremysql-data:/var/lib/mysqlDatos que tienen que sobrevivir aunque se borre el contenedor

Pregunta para la clase: mysql no tiene volumes:. ¿Qué pasa con la base alumnos si hacemos docker compose down y después up? (Se pierde: los datos vivían dentro del contenedor, y down lo borra.)

depends_on: orden de arranque, no "está listo"

Sintaxis corta (la nuestra) 
depends_on:
  - mysql

Garantiza que el contenedor de mysql arranque antes. No espera a que MySQL acepte conexiones, y eso tarda varios segundos.

Sintaxis larga + healthcheck 
depends_on:
  mysql:
    condition: service_healthy

Espera a que el healthcheck de mysql dé OK. Eso sí es "está listo".

Por eso el setup.sh tiene un bucle que repite mysqladmin ping hasta 30 veces antes de crear las tablas: depends_on solo no alcanza. Y dbexporter tiene restart: always, que lo vuelve a levantar si arrancó antes de tiempo.

networks y extra_hosts: cómo se encuentran

networks: mynetwork

Los cinco servicios están en la misma red. Docker les da un DNS interno: el nombre del servicio es su nombre de host. Por eso my.cnf dice host=mysql y prometheus.yml apunta a dbexporter:9104, sin una sola IP.

¿Hacía falta declararla?

No. Compose crea una red por defecto para el proyecto (monitoreo_default) y mete ahí a todos. Declararla tiene sentido cuando se necesitan varias redes, por ejemplo para aislar la base del resto.

extra_hosts

Agrega una línea al /etc/hosts del contenedor. host-gateway es un valor especial que significa "la IP del host". La app Flask corre afuera de Compose, en el host, y así Prometheus llega a host.docker.internal:8888/metrics.

El mismo stack, escrito hoy

# compose.yaml (sin "version")
services:
  mysql:
    image: mysql:8.4
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    volumes:
      - mysql-data:/var/lib/mysql

      interval: 5s
      retries: 20

    volumes:

      mysql:
        condition: service_healthy

  # cadvisor, prometheus y grafana: igual que antes

Los comandos del día a día

ComandoQué hace
docker compose up -dCrea la red, los volúmenes y los contenedores, en segundo plano. Si cambiaste el archivo, recrea solo lo que cambió.
docker compose psEstado de los servicios de este proyecto
docker compose logs -f grafanaLogs de un servicio, en vivo (lo de la Etapa 5, pero de contenedores)
docker compose exec mysql bashAbre una terminal dentro de un servicio que está corriendo
docker compose configValida el archivo y lo muestra tal como lo entendió Compose, con las variables ya reemplazadas. El mejor detector de errores de YAML.
docker compose downPara y borra contenedores y redes. Los volúmenes con nombre se quedan.
docker compose down -vLo mismo, y además borra los volúmenes: se pierden los datos

En Killercoda usamos docker-compose (con guion), la versión vieja. Las opciones son las mismas.

Ejercicio: encontrá los 5 errores

En grupos, 5 minutos. Este archivo no levanta, o levanta pero no hace lo que se quiere:

services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: secreta
	networks:
      - backend

  grafana:
    image: grafana/grafana:13.2.2
    ports:
      - 3000
    depends_on:
      - prometeus

  prometheus:
    image: prom/prometheus:latest
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prom-data:/prometheus

Pista: solo uno es un error de YAML. Los demás son de Compose, y uno ni siquiera da error: levanta, pero no como se esperaba.

Los 5 errores

1

Hay un tab antes de networks: en mysql. YAML no acepta tabs para indentar.

2

La red backend se usa pero nunca se declara en networks: de primer nivel. Compose da error.

3

- 3000 publica el puerto 3000 del contenedor en un puerto aleatorio del host. Para entrar por localhost:3000 va "3000:3000".

4

depends_on: prometeus: el servicio se llama prometheus. Compose da error: depende de un servicio que no existe.

5

El volumen con nombre prom-data se usa pero no se declara en volumes: de primer nivel. Mismo error que el 2, con volúmenes.

Bonus: mysql queda en backend y los otros en la red por defecto. Aunque se arreglara todo lo anterior, Grafana y Prometheus no verían a MySQL por nombre. Y docker compose config habría encontrado los errores 1, 2, 4 y 5 sin levantar nada; el 3 no es un error de sintaxis, solo hace otra cosa.

Cierre

Lo que cambió

De fig.yml a compose.yaml, de links a redes con DNS, de version: '3' a una especificación sin versión, de docker-compose a docker compose.

Lo que no cambió

La idea: describir la infraestructura en un archivo de texto, versionarlo en Git y levantarla con un solo comando.
