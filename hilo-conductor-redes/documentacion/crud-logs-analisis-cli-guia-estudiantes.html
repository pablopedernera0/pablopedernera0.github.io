Análisis de logs

Reconstruir un incidente completo —pico de carga, fuerza bruta e inyección SQL— usando solo grep, awk, sort y uniq sobre dos fuentes de log distintas. Guía de repaso con los comandos explicados pieza por pieza.

De dónde sale la evidencia

El setup.sh de esta práctica no solo levanta la infraestructura: además genera tráfico real —uso normal, un pico de carga, una fuerza bruta contra /login y varios intentos de inyección SQL— para que investigues algo que ya pasó, no algo que generás vos en el momento.

No hace falta haber hecho las prácticas anteriores en esta misma sesión: el tráfico de esta etapa es propio, generado por el mismo setup.sh.

Anatomía de un log

Los formatos varían entre servicios, pero casi cualquier línea de log de acceso o de aplicación comparte la misma anatomía de fondo:

Timestamp

Cuándo pasó. Casi siempre lo primero identificable, a veces entre corchetes o al inicio de la línea.

Origen

Quién lo generó: una IP, un usuario, un proceso, un host.

Acción / mensaje

Qué pasó: una ruta HTTP pedida, una consulta SQL, un evento del sistema.

Resultado / severidad

Cómo terminó: un código de estado HTTP, un nivel (INFO/WARN/ERROR), un código de salida.

Una vez que reconocés estas cuatro partes, leer un formato de log nuevo es cuestión de ubicar dónde cae cada una — el resto de esta guía es exactamente eso, aplicado a dos formatos concretos.

¿Dónde buscar logs?

En Linux, la convención (no una regla estricta) es /var/log/. Cada servicio suele tener su propio subdirectorio o archivo:

ServicioUbicación típica
Nginx/var/log/nginx/access.log, /var/log/nginx/error.log
Apache/var/log/apache2/ (Debian/Ubuntu) o /var/log/httpd/ (RHEL/CentOS) — access_log, error_log
MySQL/var/log/mysql/error.log, o junto a los datos en /var/lib/mysql/ (así está en este escenario: general.log)
Sistema (syslog clásico)/var/log/syslog, /var/log/auth.log, /var/log/kern.log
Sistema (systemd)journalctl — journal binario, no un archivo de texto plano
Esta app (Flask/Werkzeug)/root/crud-python/app.log, redirigido ahí a mano por el setup.sh

Cuando un servicio corre dentro de un contenedor Docker, sus logs suelen quedar dentro del contenedor en estas mismas rutas — por eso en el Paso 3 usamos docker exec <contenedor> grep ... en vez de buscar el archivo desde el host.

Mismos cuatro campos, formatos distintos

Nginx

203.0.113.5 - - [17/Sep/2026:14:02:11 +0000] "GET /api/items HTTP/1.1" 200 512 — combined log format: IP, timestamp, request, estado, bytes.

Apache

203.0.113.5 - - [17/Sep/2026:14:02:11 +0000] "POST /login HTTP/1.1" 302 - — prácticamente el mismo formato que Nginx (ambos heredan el common log format).

MySQL general_log

2026-09-17T14:02:11.123456Z 12 Query SELECT * FROM usuarios WHERE usuario='admin' — timestamp, id de conexión + tipo de comando, separados por tabs, y el SQL literal.

syslog

Sep 17 14:02:11 miservidor sshd[1234]: Failed password for root from 203.0.113.5 — timestamp sin año, host, proceso+PID entre corchetes, mensaje libre.

Distinto orden, distintos separadores — pero siempre timestamp, origen, acción y resultado, en algún orden.

El formato del log de acceso de esta app

Cada línea de app.log (formato Werkzeug, el servidor de desarrollo de Flask) tiene esta forma:

127.0.0.1 - - [04/Aug/2026 13:38:49] "GET / HTTP/1.1" 200 -
·

IP de origen — quién hizo el pedido.

·

Timestamp entre corchetes [04/Aug/2026 13:38:49] — cuándo.

·

Método y ruta entre comillas "GET / HTTP/1.1" — qué pidió.

·

Código de estado 200 — cómo respondió el servidor.

grep — filtrar líneas por patrón

grep busca un texto (literal o con expresiones regulares) y devuelve solo las líneas que lo contienen. Es siempre el primer filtro de la cadena: reduce miles de líneas de log a las pocas que importan.

UsoQué hace
grep 'patrón' archivoImprime las líneas que contienen el patrón
grep -c 'patrón' archivoCuenta cuántas líneas coinciden, sin imprimirlas
grep -- '-patrón' archivoEl -- le dice a grep "lo que sigue es el patrón, no una opción" — imprescindible si el patrón empieza con un guion

El patrón entre comillas importa: '"GET / ' incluye las comillas y el espacio final a propósito, para no matchear por accidente rutas como /login que también empiezan con /.

awk — extraer campos de cada línea

awk divide cada línea en campos y te deja imprimir el que te interesa. Por defecto separa por espacios en blanco, pero eso se puede cambiar.

UsoQué hace
awk '{print $N}'Imprime el campo N-ésimo de cada línea (contando desde 1)
awk -F'X' '{print $N}'Usa X como separador de campos en vez del espacio
awk -F'[][]'Separador con clase de caracteres: [ o ] — sirve para extraer justo lo que está entre corchetes

Si contás los campos de 127.0.0.1 - - [04/Aug/2026 13:38:49] "GET / HTTP/1.1" 200 - separados por espacio, el noveno es 200: el código de estado. Por eso $9 aparece tanto en el pico de carga como en la fuerza bruta.

El comando que arma el conteo por timestamp

grep '"GET / ' app.log | awk -F'[][]' '{print $2}' | sort | uniq -c | sort -rn
1

grep '"GET / ' se queda solo con las líneas de pedidos GET a la raíz.

2

awk -F'[][]' '{print $2}' corta cada línea por [/] y se queda con el segundo pedazo: el timestamp, sin corchetes.

3

sort ordena todos los timestamps alfabéticamente — necesario para que uniq pueda agrupar los repetidos.

4

uniq -c colapsa las líneas repetidas y antepone cuántas veces apareció cada una.

5

sort -rn ordena esos conteos de mayor a menor (-n numérico, -r reversa) — el timestamp más repetido queda arriba.

Leyendo el resultado

     60 04/Aug/2026 13:39:35
      1 04/Aug/2026 13:38:49
60

peticiones a / en el mismo segundo

60 peticiones en un único segundo es imposible de explicar como uso normal — es la firma de un pico de carga generado por una herramienta, no por personas navegando.

2. La fuerza bruta tiene otra firma

Un pico de carga se ve por volumen en un mismo endpoint. La fuerza bruta contra /login se ve por la relación entre fallos y éxitos: muchos intentos fallidos seguidos de uno o pocos exitosos.

grep '"POST /login' app.log | awk '{print $9}' | sort | uniq -c

Acá awk usa el separador por defecto (espacios) — no hace falta -F porque no estamos extrayendo el timestamp entre corchetes, sino el código de estado, que ya cae limpio en el campo $9.

Leyendo el resultado

     10 200
      4 302
200 × 10

Login que vuelve a mostrar la página con error — intento fallido.

302 × 4

Redirect a / — login exitoso. Un puñado está bien (uso normal); lo que llama la atención son los diez 200 seguidos en el mismo segundo.

Lo que el log de acceso NO puede mostrar

En ningún momento vimos qué contraseña se probó en cada intento. El log de acceso registra método, ruta y resultado — nunca el contenido del formulario que se envió.

Para ver el contenido exacto de cada intento —incluida una inyección SQL— hace falta otra fuente: el general_log de MySQL.

3. El general_log de MySQL

MySQL tiene un modo de log que registra cada consulta SQL que ejecuta, tal cual llega al servidor.

SET GLOBAL general_log = 'ON';

No está prendido por defecto: registrar cada consulta tiene un costo real de performance y de espacio en disco. Con apenas un par de minutos de tráfico de prueba, el archivo ya pesa varios KB. Se activa puntualmente para investigar, como acá.

El truco de grep -- "-- "

docker exec <mysql> grep -- "-- " /var/lib/mysql/general.log

Acá se juntan dos guiones dobles distintos, y es fácil confundirlos:

1º --

Es de grep: le dice "acá termina la lista de opciones, lo que sigue es el patrón" — necesario porque el patrón que buscamos empieza con un guion, y sin el -- grep lo tomaría como una opción inválida.

2º "-- "

Es el patrón que buscamos: dos guiones seguidos de un espacio, que en SQL es el inicio de un comentario — la firma clásica de una inyección que corta la consulta original y comenta el resto.

Lo que encuentra ese grep

SELECT id, usuario FROM usuarios WHERE usuario = 'admin' -- ' AND password = 'x'
SELECT id, usuario FROM usuarios WHERE usuario = '' OR '1'='1' -- ' AND password = 'x'

El propio texto de usuario reescribe la consulta: cierra la comilla, agrega su propia condición, y comenta con -- todo lo que venía después (incluida la verificación de la contraseña).

A diferencia de la fuerza bruta —que prueba contraseñas contra un usuario normal— acá el ataque está en el propio campo usuario. El log de acceso de la app nunca lo hubiera mostrado.

4. Correlación: una sola línea de tiempo

Ningún log por separado cuenta la historia completa. paste permite juntar dos columnas (dos comandos) lado a lado:

grep '"POST /login' app.log | awk '{print $9}' \
  | paste - <(grep '"POST /login' app.log | awk -F'[][]' '{print $2}')

paste - toma la entrada estándar (los códigos de estado) y la pega columna por columna junto a la salida de otro comando (los timestamps), usando <(...) —sustitución de proceso— para tratar ese segundo comando como si fuera un archivo.

Dos fuentes, dos historias parciales

Log de acceso de la app general_log de MySQL
Volumen, timing, ruta, código de estado La consulta SQL exacta, incluida la inyectada
No muestra el contenido del formulario No muestra nada del tráfico HTTP en sí (IP real, headers)

Investigar un incidente real casi siempre implica correlacionar varias fuentes de log, no una sola.

ComandoPara qué sirve

Para llevarte

Todo lo que hiciste hoy fue manual: ir a buscar un archivo, filtrarlo, contar líneas. Funciona, pero no escala si hay que revisar esto todos los días o la infraestructura crece a más de un servidor.
