Logs vs. métricas

LogMétrica
Un evento: una línea por petición, con todo el detalleUn número que cambia en el tiempo
10.0.0.5 - - [24/Sep] "POST /login" 401http_requests_total{status="401"} 1832
Responde: qué pasó exactamente, con quién, cuándoResponde: cuánto, qué tan rápido, está subiendo o bajando
Crece con el tráfico (más requests = más líneas)Tamaño casi fijo (un contador no ocupa más por contar más)
Se usa para investigar despuésSe usa para detectar y alertar en el momento

No compiten: en producción se usan las dos. La métrica te avisa que algo anda mal; el log te dice qué fue.

Qué es, exactamente, una métrica

Para Prometheus, una métrica es una serie temporal: un nombre, un conjunto de etiquetas, y una lista de pares (momento, valor).

flask_http_request_duration_seconds_count{method="GET", path="/", status="200"}  4213
└─────────────── nombre ──────────────┘└──────────── etiquetas ───────────────┘  valor
Contador (counter)

Solo sube (o vuelve a 0 si el proceso se reinicia). Ej: peticiones atendidas, queries ejecutadas. El valor absoluto dice poco; importa cuánto sube por segundo.

Medidor (gauge)

Sube y baja. Ej: conexiones abiertas a MySQL, memoria usada. El valor actual ya dice algo por sí solo.

Cada combinación distinta de etiquetas es una serie distinta: status="200" y status="500" son dos series.

Cómo se ve por dentro: /metrics

Una app "instrumentada" expone sus números como texto plano en un endpoint HTTP. En la práctica, la librería prometheus-flask-exporter lo agrega a la app sin tocar su lógica.

$ curl -s http://127.0.0.1:8888/metrics | head
# HELP flask_http_request_duration_seconds Flask HTTP request duration in seconds
# TYPE flask_http_request_duration_seconds histogram
flask_http_request_duration_seconds_count{method="GET",path="/",status="200"} 57.0
flask_http_request_duration_seconds_sum{method="GET",path="/",status="200"} 0.84
# HELP flask_http_request_total Total number of HTTP requests
# TYPE flask_http_request_total counter
flask_http_request_total{method="GET",status="200"} 57.0

Esto es todo lo que Prometheus lee. No hay magia: es un curl repetido cada 5 segundos.

Pull, no push: el scrape

Push

El servicio manda sus datos

Cada app tiene que saber a dónde enviar. Si el receptor se cae, los datos se pierden o se acumulan. Si una app muere, simplemente deja de mandar... y nadie se da cuenta.

Pull (Prometheus)

Prometheus va a buscarlos

Tiene una lista de targets y cada scrape_interval (5s en la práctica) hace un GET a cada uno. Si un target no responde, eso ya es un dato: up = 0.

# prometheus.yml (el que genera setup.sh)
global:
  scrape_interval: 5s
scrape_configs:
  - job_name: 'cadvisor'   → cadvisor:8080
  - job_name: 'mysql'      → dbexporter:9104
  - job_name: 'crud-app'   → host.docker.internal:8888

¿Y si el servicio no habla "Prometheus"?

MySQL no tiene un /metrics. Docker tampoco. Para eso existen los exporters: programas chicos que consultan el estado de un sistema y lo traducen al formato de texto de Prometheus.

FuenteCómo expone métricasEjemplo de métrica
App FlaskDirecto: la librería agrega /metrics a la appflask_http_request_total
MySQLmysqld-exporter (servicio dbexporter): se conecta a MySQL, corre SHOW GLOBAL STATUS y lo traducemysql_global_status_threads_connected
ContenedorescAdvisor: lee los cgroups del kernel, donde Linux lleva la cuenta de CPU/memoria/red de cada contenedorcontainer_cpu_usage_seconds_total

Hay exporters para casi todo: Linux (node_exporter), Nginx, PostgreSQL, Redis, routers vía SNMP. El patrón es siempre el mismo.

Tres detalles de red en el diagrama

Nombres de servicio, no IPs

Grafana se conecta a http://prometheus:9090, no a localhost. Dentro de la red de compose, Docker resuelve cada nombre de servicio a la IP del contenedor, igual que la app encuentra a mysql.

localhost depende de quién pregunta

Dentro del contenedor de Grafana, localhost es el propio Grafana. Por eso poner localhost:9090 como fuente de datos falla, aunque desde el navegador funcione.

Salir de la red de compose

La app Flask corre en el host, fuera de compose. Prometheus la alcanza por host.docker.internal, un nombre que el extra_hosts: host-gateway del compose apunta a la IP del host.

Consecuencia práctica: lo que ves en Grafana tiene hasta ~10 segundos de atraso (scrape + refresco). Es "tiempo real" a escala humana, no al milisegundo.

PromQL, paso 1: up

Prometheus genera por su cuenta una métrica por cada target: up. Vale 1 si el último scrape funcionó y 0 si no.

up
up{instance="cadvisor:8080",            job="cadvisor"}   1
up{instance="dbexporter:9104",          job="mysql"}      1
up{instance="host.docker.internal:8888", job="crud-app"}  1
up{instance="localhost:9090",           job="prometheus"} 1

Es la misma información que la pantalla Status → Targets, pero como dato: se puede graficar y, sobre todo, se puede alertar con ella (up == 0 durante 1 minuto → avisar).

PromQL, paso 2: filtrar por etiquetas

mysql_global_status_threads_connected            # gauge: conexiones abiertas ahora

flask_http_request_total{status="200"}           # solo respuestas OK
flask_http_request_total{status=~"5.."}          # regex: cualquier 5xx
container_cpu_usage_seconds_total{id=~".*abc123.*"}   # un contenedor puntual
OperadorSignificado
=igual
!=distinto
=~coincide con la expresión regular
!~no coincide con la expresión regular

PromQL, paso 3: por qué rate()

Un contador solo sube. Graficado tal cual, un pico de carga se ve como una pendiente más empinada — difícil de leer. rate() calcula cuánto subió por segundo en una ventana de tiempo.

Contador crudo

flask_http_request_duration_seconds_count

Con rate(...[1m])

requests por segundo: el pico se ve de un vistazo

Regla práctica: contador → siempre con rate(). Gauge → directo. El [1m] es la ventana: más corta reacciona más rápido pero es más ruidosa.

Un caso real: cAdvisor sin nombres

En una PC de desarrollo, cAdvisor etiqueta cada contenedor con name e image. En Killercoda no: cada contenedor aparece solo como el ID de su cgroup.

container_cpu_usage_seconds_total{cpu="total", id="/system.slice/docker-3f9a1c...e21.scope", ...}
1

{name="mysql"} no devuelve nada: la etiqueta no existe en este entorno.

2

El ID corto de docker ps -qf "name=mysql" es un pedazo del ID completo del cgroup.

3

Entonces se filtra por regex: {id=~".*<id corto>.*"}. El script query_cpu_mysql.sh arma esa consulta por vos.

Lección general: las etiquetas que tenés dependen del entorno donde corre el exporter. Antes de escribir un filtro, mirá qué etiquetas trae realmente la serie. Este problema lo detectó una compañera en clase.
