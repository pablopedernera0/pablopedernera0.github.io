Infraestructura de Redes · Trabajo n°7

Instructivo de despliegue

Reciben una aplicación ya construida y la tienen que poner en funcionamiento, en equipo, como lo haría un área de administración de red. Este documento es el pedido de trabajo.

El escenario

Un equipo de desarrollo les entrega una aplicación ya construida y les pide que la pongan en funcionamiento. No escriben una línea de código de la app — reciben el Dockerfile ya armado — y son responsables de todo lo que hace falta alrededor: red, persistencia de datos, configuración, y la documentación de por qué tomaron cada decisión.

Trabajan en equipo, cada integrante en su propia sesión de GitHub Codespaces — no hace falta PC propia, corre en el navegador — así que la coordinación pasa por el repositorio de GitHub: cada uno prueba en su sesión, y sincronizan por push/pull.

Lo que reciben

El código y el Dockerfile

pablopedernera0/crud-python, rama trabajo7-deploy. El Dockerfile ya está armado y no se toca.

El esquema de la base

init.sql, en ese mismo repo: crea las tablas que usa la app y carga un usuario de prueba. Cómo aplicarlo al levantar la base es parte de la decisión.

Este instructivo

Nada más. No hay un docker-compose.yml de partida — ese es el trabajo.

Cómo arrancar

1

Un integrante hace fork de crud-python (rama trabajo7-deploy, no main) a la cuenta de GitHub del equipo. Ese fork es el repositorio de entrega.

2

El resto del equipo clona ese fork (no el original), para tener permiso de push.

3

Cada integrante abre su propia Codespace sobre el fork: Code → Codespaces → Create codespace. No hace falta instalar nada, ni Docker.

4

Diseñan y prueban el docker-compose.yml ahí, sincronizando por git push/git pull como con cualquier repo.

Qué tiene que cumplir — funcionamiento

Esto es lo que se va a evaluar. No hay requisitos ocultos más allá de esta lista.

1

La aplicación queda accesible desde el navegador del host, en un puerto conocido.

2

La aplicación se conecta a la base de datos resolviendo por nombre de servicio, no por una IP fija.

3

La base de datos arranca con el esquema y los datos que la aplicación necesita para funcionar.

Qué tiene que cumplir — persistencia y configuración

4

Los datos de la base no se pierden si el contenedor se reinicia o se recrea.

5

Ninguna credencial ni dato sensible está escrito en el código ni en la imagen — se puede cambiar sin reconstruir nada.

Qué tiene que cumplir — documentación y proceso

6

Cada decisión de infraestructura (por qué esa red, ese volumen, esa forma de pasar credenciales) queda documentada y justificada en el repo — no alcanza con que funcione, tiene que poder explicarse.

7

El historial de commits refleja el proceso de decisión del equipo: mensajes que dicen qué se decidió y por qué, no solo qué archivo se tocó.

Herramientas que van a necesitar

Las siguientes secciones explican conceptos de Docker, no la solución a este despliegue en particular. Qué servicio necesita cuál herramienta, y cómo aplicarla acá, es parte de la decisión del equipo.

Persistencia con volúmenes

Para que los datos de un servicio sobrevivan a un reinicio o a que se recree el contenedor, Docker permite montar volúmenes: un espacio de almacenamiento que vive fuera del ciclo de vida del contenedor.

services:
  algun-servicio:
    volumes:
      - nombre_del_volumen:/ruta/dentro/del/contenedor

volumes:
  nombre_del_volumen:

Documentación oficial: docs.docker.com/engine/storage/volumes

Redes y resolución por nombre

Cuando varios servicios están definidos en el mismo docker-compose.yml, Docker Compose los conecta automáticamente a una red donde cada uno puede resolver a los demás por el nombre del servicio, sin necesidad de conocer una IP.

Documentación oficial (incluye cómo definir redes propias si hace falta separar servicios): docs.docker.com/engine/network

Variables de entorno

Para pasar configuración (credenciales, hosts, puertos) sin escribirla en el código ni en la imagen, los servicios pueden recibir variables de entorno definidas en el docker-compose.yml, o cargadas desde un archivo aparte.

Documentación oficial: docs.docker.com/compose/how-tos/environment-variables

Cómo se corrige

En el parcial se revisa lo ya subido a GitHub y se hacen preguntas puntuales a cada integrante sobre decisiones tomadas, para confirmar comprensión y aporte individual dentro del trabajo grupal.

No se evalúa el contenedor andando — se evalúa si pueden explicar por qué lo armaron así.
